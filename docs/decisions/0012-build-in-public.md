# 0012 边做边公开,内容需求进入开发方案

- 日期:2026-11-16
- 状态:生效
- 决定者:项目负责人

## 背景

项目刚完成核心逻辑和文档基础,还没有界面和美术。负责人希望把设计思路和开发进度做成内容,
发在小红书、抖音和微信公众号上,并且认为内容的质量决定了有没有人看,所以要在开发之初就把这件事考虑进去。

## 决定

- 在开发过程中持续对外发布内容,平台是小红书、抖音、微信公众号。
- 内容以设计思路和开发进度为主。
- 做内容所需要的东西(画面、素材、工具)作为开发方案的一部分提前安排,而不是事后补。

具体怎么做见[内容策略](../marketing/01-content-strategy.md)。其中的受众、主线、平台分工等是建议,尚待负责人确认。

## 理由

- 上线前就有人知道、有人等,比做完再找人容易得多。
- 更重要的是它能提前验证需求:目标用户对这个想法有没有反应,在投入几个月之前就能知道。
- 原型需要真人试玩,内容是找到这些人的途径。
- 素材只在开发过程中存在。中间状态的截图、被否决的方案、当时的数字,事后很难补回来。

## 被否决的方案

- **做完再宣传。** 失去了提前验证需求的机会,而且开发过程中的素材留不下来。

## 后果

- **美术方向要提前定。** 每篇内容都需要画面和统一的风格,原计划的"先用占位图"不够了。
- **路线图的顺序调整。** 先做看得见、能录下来的农场切片,正式词库后移。
- **新增两个工具需求。** 快进时间(原本就有)兼作延时拍摄;用模拟器生成演示存档。
- **新增一个流程步骤。** 每个里程碑留下截图、数字,并在选题库登记。
- **做内容会占用开发时间。** 一个人开发,这是真实的代价,需要设定上限。
- **对外发布之前必须先完成名称查重。**
- **对外内容同样要遵守诚实的要求。** 模拟数字要注明,不夸大学习效果。
- 开发日志天然吸引开发者而不是玩家,关注者不等于用户。这一点需要在选题和表达上刻意对冲。
